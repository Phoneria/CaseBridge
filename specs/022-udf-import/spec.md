# UDF (UYAP Doküman Formatı) import and the read text in "Belgeden doldur" (application v.0.53, unreleased)

User request (18 Nov–24 Nov 2026): as the first, risk-free step of UYAP integration, accept the `.udf` files lawyers download from UYAP wherever CaseBridge accepts documents and read their text, so Dosya Analizi, Canlı Duruşma, AI fill and the privacy tool work with real UYAP documents. Follow-up (24 Nov): after "Belgeden doldur", show the text that was read from the uploaded file. Exporting or creating UDF files is out of scope. Design notes: `docs/superpowers/specs/2026-11-24-udf-import-design.md`.

## User Scenarios
1. A lawyer downloads "Bilirkişi Raporu.udf" from UYAP and uploads it in a case's Belgeler tab. The list shows a UDF badge, the reader shows the document text (headers, footers and table cells included), and "İndir" returns the original file byte for byte so it still opens in UYAP Doküman Editörü.
2. A scanned UDF (image only) or a broken download is still saved, without text; the reader says "Bu belge için metin çıkarılamadı". In "Belgeden doldur" the same file gets "Bu belgeden metin çıkarılamadı…" and no AI call.
3. On the new-case form the lawyer chooses `dilekce.udf` and presses "Doldur". The fields are drafted and a closed section "Belgeden okunan metin (dilekce.udf)" shows exactly what the AI read, so the draft can be checked against it; for a long document a note says only the first part was read.
4. In the privacy tool a UDF is read as format "UDF" with a fixed warning that tables became plain text and images and formatting were not read; an OpenDocument (.odt) file is not mistaken for a UDF.
5. A hostile file named `.udf` (zip bomb, XML entity tricks, deep nesting, thousands of elements) is rejected or read within fixed limits, and no error message or log line contains document text.

### Functional Requirements
- **FR-001**: `.udf` (any letter case) is accepted by case document upload (including the case-close "Karar belgesi"), AI fill from document, the privacy tool and the CLI import. Every frontend file picker lists `.udf` from one shared extension list, the copy names UDF, and the documents type filter offers UDF.
- **FR-002**: The UDF text is the text of `content.xml` → `<template>` → first direct `<content>` child (CDATA or escaped text) with `\r\n` and `\r` turned into `\n`. Headers, footers and table cells are part of that text. `sign.sgn`, `documentproperties.xml` and embedded media are never opened. The reader (`backend/app/services/udf_reader.py`) uses the standard library only.
- **FR-003**: Safety limits: at most 512 ZIP members and 16 MB expanded size; encrypted or duplicate members, a `DOCTYPE`, a root other than `template` and nesting deeper than 64 levels are rejected. No element tree is built, so memory follows the text size. Declared encodings such as `windows-1254` and Java-style names such as `UTF8` are read. Errors carry one of two fixed Turkish messages and never document content.
- **FR-004**: The original bytes are stored unchanged. Downloads from the case documents route and the workspace/client-portal route return them as `application/octet-stream` with the `.udf` name. A broken or text-less UDF is saved with `extracted_text` null.
- **FR-005**: The `documenttype` enum gains `udf` (PostgreSQL `ALTER TYPE … ADD VALUE IF NOT EXISTS`, no-op elsewhere; downgrade keeps the value). Merge revision `f3a5c7e9b1d2` joins the UDF head with main's chat-sources head so `alembic upgrade head` has a single head.
- **FR-006**: Privacy tool: a ZIP with `content.xml` and neither `word/document.xml` nor `mimetype` is read as a UDF in the isolated worker and returned with format `udf` and the warning "UDF içindeki tablolar düz metin olarak alındı; görseller ve biçimlendirme okunmadı." An ODT keeps the existing generic error; a UDF without text gets the existing OCR message.
- **FR-007**: `POST /case-intake/extract` reads UDF files; an unreadable UDF is a 422 with the existing hint. The response adds `source_text`: exactly the text sent to the model (the first `case_intake_max_chars`, 30,000, characters).
- **FR-008**: "Belgeden doldur": after a fill from a file, a closed-by-default section "Belgeden okunan metin (<file name>)" shows `source_text` in a scrollable, focusable region, with "Belge uzun olduğu için yalnızca AI'ın okuduğu ilk kısım gösteriliyor." for a long document. It is not shown for pasted text and disappears when another file is chosen, the mode changes, a new fill starts or the overwrite is declined.
- **FR-009**: Application version: after every main merge `frontend/app-version.json` is regenerated with `frontend/scripts/update-version.mjs` from main's manifest (never hand-edited) and passes `--check`; v.0.53 after merging main v.0.52.

## Success Criteria
- Reader tests prove the text source, normalization, encodings, every limit, DOCTYPE rejection without leaking text, the depth cap and a bounded memory peak for 400,000 elements.
- API tests prove upload, original-byte download on both routes, uppercase extension, text-less saving, intake reading and `source_text`, privacy-tool format/warning/ODT/OCR cases, CLI import and the migration chain on SQLite (also tried on PostgreSQL 16).
- Frontend tests prove the shared `.udf` pickers and copy, the UDF filter, the privacy tool's UDF format and every state of the read-text section.
