# Benzer Davalar sidebar: similar precedents, stages 1–3 (application v.0.49, unreleased)

User request (24 Nov 2026): a "Benzer Davalar" sidebar on the case page that ranks the bureau's own precedents against the open case and explains, only from stored data, why each one is similar. Stage 1 is the backend similarity engine; stage 2 is the sidebar. Stage 3 (follow-up request, 24 Nov 2026) adds filters, a summary, per-precedent details (value, duration, rule-based differences, timeline, score breakdown), a side-by-side comparison and an optional, explicitly requested AI explanation with timeout and fallback. Builds on specs/018-similar-cases (same normalisation and court types); no new infrastructure.

## User Scenarios
1. A lawyer opens a case, clicks "Benzer Davalar" and sees the closest precedents of their bureau with a 0–100 score, category, court, result and decision date.
2. For each precedent the lawyer sees the matching structured fields and shared statute or Yargıtay references, and can expand "Neden benzer?" to read the shared key terms and 1–3 passage pairs (this case ↔ precedent) with the shared words highlighted.
3. A user who may edit the case links or unlinks a precedent from the sidebar; anyone can open the precedent.
4. Another bureau's precedents never appear and no explanation contains text that is not stored for the case or the precedent.
5. The lawyer reads a one-line summary ("12 emsal · 8 kazanıldı · 3 kaybedildi · ort. 14 ay"), narrows the list by result, court and minimum similarity, sorts it, and opens a precedent to see its score breakdown, the path it followed, the key differences and a side-by-side comparison with the case.
6. On request the lawyer gets a short AI explanation built only from the two stored texts; when AI is off, slow or fails, a summary of stored data is shown instead and the rest of the sidebar is never delayed.

### Functional Requirements
- **FR-001**: Candidates are only the session bureau's precedents (`is_precedent`, filtered by `law_firm_id`); ordinary cases are never returned. Document text is read with the same bureau filter.
- **FR-002**: `GET /cases/{id}/similar-precedents?limit=5` (1–20) returns `{summary, source, items}` (stage 3; the stage-2 list shape had no other consumer and was never released, so it was replaced rather than kept). Access follows the existing read rules: another bureau's case, a precedent id or an unknown id is 404, restricted workspace accounts 403, anonymous 401. Every result opens through `GET /precedents/{id}` for the caller.
- **FR-003**: Turkish-aware normalisation: dotted/dotless I lower-casing, folding, punctuation removal, a small stopword list, simple suffix trimming (at most two suffixes, 4+ letter stem, a one-letter suffix only as the last one).
- **FR-004**: A case's text is case_name, claim, facts_summary, plaintiff_position, defendant_position, description, closing_note and up to 8000 characters of extracted document text.
- **FR-005**: Score 0–100 = 0.6 TF-IDF cosine (pure Python) + 0.2 same case_type + 0.1 court (same court or court type 1.0, same family 0.5) + 0.1 share of the source's statute references found in the precedent. A signal the source cannot provide (no court, no reference, no text) leaves the denominator. A precedent needs cosine ≥ 0.05 or the same category.
- **FR-006**: Statute references are extracted by regular expressions: "TBK 49", "İİK m. 67", "HMK md. 107", "TBK'nın 344. maddesi", "4857 sayılı … Kanunu'nun 18. maddesi" and "Yargıtay <daire> <yıl>/<no> E. <yıl>/<no> K." in either order; a Yargıtay reference without K. matches the same docket with K.
- **FR-007**: Each result returns precedent_id, case_number, case_name, case_type, court, outcome, decision_date, score, text_score, linked_to_case and an explanation: up to 8 shared key terms, shared statute references, matching structured fields (category, court, close case value) and 1–3 passage pairs with source labels and highlight offsets.
- **FR-008**: Anti-hallucination: every extractive explanation string is copied from the stored case, precedent or document text; highlights mark only words both sentences share. No LLM is called unless `explain=true` (FR-016), and that path keeps the rule of `backend/app/ai/agents/common.py`.
- **FR-009**: The precedent corpus is cached in memory per bureau; the key includes the bureau's precedent count and latest `updated_at` and its precedent documents' count and latest upload, so a changed precedent or a new document rebuilds it.
- **FR-010**: The case overview has a "Benzer Davalar" button that opens a right-hand sidebar (dialog, Escape and close button, focus returns) listing up to 8 precedents with score, badges, matching fields and statutes, an expandable "Neden benzer?" with terms and highlighted passage pairs, "Emsali aç" (`/emsaller?karar=<id>`), and for users who may edit the case "Bu davaya bağla" / "Bağlantıyı kaldır". Loading, empty and error states; a note that explanations come only from stored data. All UI text is Turkish and uses existing theme tokens. Application version v.0.49. Stage 3 widens it per FR-015.
- **FR-011**: Optional filters `outcome` (repeatable CaseOutcome), `court` (exact court name, Turkish case-insensitive), `min_score` (0–100) and `precedent_id` narrow the ranked list; an invalid value is 422. Filters never widen the bureau scope.
- **FR-012**: `summary` covers every match after the filters (not only the first `limit`): count, outcome counts, average duration in months and average case value with the number of rows each average uses (null when no row stores the value), the unfiltered list of courts for the court filter, and the signals left out of the score for this case.
- **FR-013**: Each item adds `case_value`, `duration_months` (opening_date → decision_date, one decimal, null unless both are stored and ordered), `score_breakdown` (points and maximum per signal, adding up to the score), `timeline` (the precedent's CaseEvents of the same bureau, ordered by date, at most 25: date, type, title) and `facts` (the stored facts compared side by side); `source` holds the same facts for the case.
- **FR-014**: `key_differences` are rule-based and fire only when both files store the fact: category, client role, court type, expert report (an expert_report event or the term in the text), evidence families named in the text (witness, contract, notice, invoice, messages, photos, inspection, minutes, medical report, payroll/SGK, land registry), uploaded documents present or not, and case values more than 2× apart.
- **FR-015**: Sidebar stage 3: summary header, result chips, court select, minimum-similarity slider (debounced), client-side sort (similarity, decision date, duration, value), duration and amount on cards, a detail view in the drawer (score breakdown, "Neden benzer?", "Temel farklar", "İzlenen yol" in the Gelişmeler timeline style, "Yapay zekâ açıklaması" button with loading, answer, fallback notice and error states) and a "Karşılaştır" mode that shows this case and the precedent side by side and marks comparable facts that differ. The older "Benzer davalar" card stays (FR-017).
- **FR-016**: `explain=true` adds `ai_explanation {status: ai|fallback, text, notice}` per returned item. The prompt holds only the two stored texts and the extractive explanation plus the no-fabrication clause; calls run in a bounded thread pool with a total deadline (`SIMILARITY_EXPLAIN_TIMEOUT_SECONDS`, default 12). Timeout, provider error, empty answer, AI off (`LLM_PROVIDER=mock` or no key) or an answer citing a statute/decision absent from both texts give the extractive fallback with a Turkish notice; the endpoint still answers 200. The sidebar list never asks for it; only the button does, for one precedent.
- **FR-017**: The case page keeps the stage-1 "Benzer davalar" card: it lists same-bureau ordinary cases as well as precedents and links to the full search page, which the precedent-only sidebar does not cover.
